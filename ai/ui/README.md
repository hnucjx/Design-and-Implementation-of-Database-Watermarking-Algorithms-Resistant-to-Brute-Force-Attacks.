# 界面缺陷记录（ui）

本目录记录**每一处界面缺陷与设计瑕疵**：一个问题 = 一个文件 = 一个 commit。

它与 [修复记录（bug-fix）](../bug-fix/README.md) 分工不同：

| | 记什么 | 典型症状 |
|---|---|---|
| `ai/bug-fix/` | **功能坏了** | 报错、任务失败、数据被破坏 |
| `ai/ui/`（本目录） | **界面不对** | 能跑、不报错，但呈现错位、不一致、说不清 |

之所以要单独开一个目录，是因为第二类问题的处境最糟：它**没有堆栈、没有失败用例**，
唯一的证据是「用户看了一眼觉得不对」。这种问题要么被当成主观意见拖下去，
要么被「看着还行」蒙过去。所以本目录的硬要求是：

> **必须把「肉眼看到的差异」变成可测量的数字。**

只有一句「看着不齐」的记录视为未完成。至少要给出：哪个元素、哪个属性、差多少像素、
用什么命令量出来的。

## 记录约定

每个文件按固定小节写，宁可写「未验证」也不要写猜测：

| 小节 | 要求 |
|---|---|
| 问题 | 用户能观察到的现象（截图 + 坐标），不是代码现象 |
| 原因 | 具体到文件/行/属性，附**实测**证据（命令与输出），不写「可能是」 |
| 修复方案 | 改了什么、为什么这么改、**为什么不选另一种改法** |
| 效果 | 修复前后的可对照数字（差几像素、行高多少） |
| 验证 | 自动化断言 + 真实浏览器实测 + 回归结果；新增的断言要**先证明它能抓住这个缺陷** |
| 风险与回滚 | 副作用、回滚方式；影响到别的断点/主题的必须写清 |
| 关联 | 指向相邻缺陷，说明是否同一类失败 |
| 未覆盖 / 如实说明 | **必填的诚实项**：这类缺陷的自动化覆盖边界在哪、本轮没验到的地方 |

记录的插图放 `ai/ui/assets/NNN-*.png`（目前只有 003 用到）：改动是**视觉**的、
而 `docs/assets/screenshots/` 里那四张拍的是默认状态、看不出差别，所以对照图随记录走。
图必须**自解释**（把「哪个是修复前、差多少像素」画在图上），并写清它是怎么生成的 ——
003 的「修复前」那张是用承重注入还原的渲染，不是历史截图，不得当成历史截图引用。

## 一条通用约定：这类缺陷的自动化覆盖边界

本仓库的前端测试跑在 **jsdom** 上，jsdom **不做布局**：`getBoundingClientRect()` 一律返回 0，
`getComputedStyle()` 也算不出真实的盒模型。因此

- **「两个东西是不是对齐」永远无法用单测断言**；
- 能进单测的只有**样式源文层面的不变式**（例如「某个基类不许声明纵向外边距」）；
- 真正的判据是 **CDP 探针 + 真实浏览器实测**：headless Edge + CDP，量 `getBoundingClientRect()`
  与 `getComputedStyle()`，并截图。探针放在被 gitignore 的 `tmp_acceptance/` 下（不进 CI，故非自动化覆盖）。

记录里必须写清哪一部分被自动化覆盖、哪一部分只靠人工/探针，不许含糊成「已修复」。

## 已知但**未处理**的界面问题（下一轮候选）

1. **解析后，标签里可能出现一个在界面上摘不掉的语言。**

   `applyAnalysisResult()` 每次解析都把选择重置成 settings 的默认值
   （`App.tsx` 的 `applyAnalysisResult()`：`subtitle_languages: settings?.default_subtitle_languages ?? …`，
   出厂默认是 `["en"]`；2026-10-02 重构前该行在 `App.tsx:163`）。如果这个视频**没有** `en` 字幕轨，标签会写「已选 1 项：en」，
   而下拉列表里（只列该视频可用的语言）**没有对应的复选框**，用户没有任何办法把它去掉
   —— 他会带着一个自己并不想要、且无法取消的字幕语言去建任务。

   本轮实测复现过这个状态（003 的探针里 `en` 一直挂在标签开头；那个 12 种语言的视频
   确实没有 `en` 轨）。但**本轮没有查证它的下游影响**：带着一个不存在的语言提交任务后，
   后端是忽略、跳过、还是失败，属 `ai/bug-fix/` 的范围，未验。候选记录：`ai/ui/004`
   （下游若是失败，则应改记到 `ai/bug-fix/`）。

2. **贴右边缘的说明浮层，右缘比布局视口宽出约 3px。**

   `HelpPopover.place()` 用 `window.innerWidth` 算右边界，而它**含滚动条**
   （1440 窗口下 `document.documentElement.clientWidth = 1425`，差 15px）。
   浮层于是落在 `left=988`、`width=440` → `right=1428`，比布局视口多 3px。

   **不是新增的缺陷**：同一栏里既有的「常用端口」浮层量到完全相同的 `left=988 / right=1428`
   （1440px，实测见 `tmp_acceptance/ui_aria2c_help.py` 的第 [6] 段，那段专为对照而设）。
   影响很小：固定定位元素不产生横向滚动条（整页 `overflowX = 0`），浮层本身
   `scrollWidth - clientWidth = 0`、后代也没有内部溢出，这 3px 落在浮层的 `padding: 12px 14px`
   与阴影上，文字未被裁。
   候选记录：`ai/ui/005` —— 把 `place()` 里的 `window.innerWidth` 换成
   `document.documentElement.clientWidth` 即可，但那是共用组件的行为变更，
   需连同 42 项浮层探针（`ui_help_popover_check.py`）一起回归，不与文案改动混在一次提交里。

3. **窄屏（390px）下任务卡片的标题被挤成一列单字。**

   做 [009](009-page-level-errors-scroll-out-of-view.md) 的窄屏对照图时顺手拍到的：
   1440→390 之后，任务卡片头部那一行是「标题 + 8 颗图标按钮」，按钮不换行、也不收缩，
   标题这一侧只剩 ~30px ⇒ 中文按**一个字一行**竖排下来（截图见
   `tmp_acceptance/error-banner-mobile-scrolled.png` 的下半部分）。

   **不是 009 引入的**：009 只加了 `.error-banner*` 与一条 `@media` 里的内边距，
   没有碰 `.job-card` / `.item-row` / `.item-actions` 的任何声明；这条在本次改动之前
   就已经如此（同一份 390px 渲染里，报错条之外的部分全都还是老样子）。

   未处理，因为它需要重新安排窄屏下的操作区（换行成第二排、或收进「更多」菜单），
   属于版式设计决定，不与一条错误提示的修复混在一起。下一轮先量：390px 下标题列的实际
   可用宽度、按钮行占多宽、以及折成两排后卡片高度涨多少。
