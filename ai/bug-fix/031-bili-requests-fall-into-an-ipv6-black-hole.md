# 031 · 点「扫码登录」「重新体检」都只得到一句「超时」：B站 请求实际走了 160 秒

## 问题

两条反馈，看起来是两件事：

1. 点**「扫码登录」**，页顶出现一条错误，说的却是**另一个接口**：
   `请求超时：60 秒内后端没有响应（/api/bilibili/uploads/cab…/retry）`
2. 点**「重新体检」**，每次都只有离线结论：`账号探测 12 秒还没回来（本机直连 B站 时域名解析可能卡住）`

## 取证

### 先排除一个假线索

日志里**当晚没有** `POST /api/bilibili/login/qrcode`，也没有 `GET /api/bilibili/status?probe_account=true`。
一开始很容易推成「前端把请求发错了」或「浏览器连接被轮询挤爆」。都不成立 —— 先记下这条，
因为它决定了往哪儿找。

### 直接量

起一个真实后端（8010 空着，用 8013），`curl --noproxy`：

```
probe_account=true  →  45 205 ms（curl 的 45 秒上限先到，HTTP 000）
qrcode              →  >45 s
```

日志里看不到它们，是因为 **uvicorn 的访问行在响应完成时才写**：请求还在跑，客户端先断了。

### 根因

`bili_http.DEFAULT_TIMEOUT = 20.0` 写得好好的，为什么走了 160 秒？因为 **`timeout` 是单次
socket 操作的预算，不是这次请求的总时长**。`socket.create_connection` 会把解析出来的**每个地址**
都试一遍，每次都拿满 `timeout`。

本机 `getaddrinfo` 正常（0.02 s），但返回的前 6 个都是 IPv6，而**本机到 B站 的 IPv6 是黑洞**：
连上去没有任何回应。于是 6 × 20 s ≈ 120 s 起步：

| 场景 | 实测 |
| --- | --- |
| 默认顺序（IPv6 先） | **160.19 s** |
| 强制 IPv4 | **0.44 s** |

（同一台机器、同一个 URL、同一个 `urllib`。差的不是网络好坏，是**先试哪个地址族**。）

这就同时解释了两条反馈：

- **重新体检**：后端要 160 s，前端 12 s 的预算必然先到 ⇒ 每次都只拿到离线结论。
- **扫码登录**：同一个传输层 ⇒ 请求挂 60 s 以上，前端 60 s 超时先到；而**用户看到的红条
  是上一条别的动作（重试投稿）遗留的** —— 错误横幅是页面级的，谁先落定谁先写，后来的人照读。

### 第二层缺陷（同一段代码里）

1. **前端预算比后端短**：`CHECK_TIMEOUT_MS = 12_000` < `bili_http.DEFAULT_TIMEOUT = 20 s`。
   即使传输层修好，一次 12~20 秒的**正常**往返也会被报成「超时」—— 那句「超时」是假的。
2. **探测失败时什么都不给**：`runHealthCheck` 对网络错误直接抛，界面于是只留一条红条，
   **面板还是上一次的旧结论**。而离线那一半（投稿工具、登录文件）根本不需要网络，
   没有理由因为探测失败就整块不给。
3. **超时消息不点名动作**：只给 URL。`/api/bilibili/uploads/<id>/retry` 里没有一个字是用户认识的，
   于是「重试投稿超时」被读成「扫码登录失败」。
4. **旧错误不清理**：开始新动作时不清页顶那条红条，用户先看到的是别人的错误。

## 修复

### 后端（根因）

`bili_http.py` 新增一对连接类与 `_connect_within`：

- **只解析 IPv4**（`getaddrinfo(host, port, AF_INET, SOCK_STREAM)`）。
- **整段共享一个截止时刻**：每个地址的 socket 超时取「剩余预算」，用完就不再试下一个。

两处都写进模块文档：IPv6 黑洞是本机事实，总预算是调用方写 `timeout=20` 时真正想要的语义。

**取舍**：预算用完就不再试后续地址 ⇒ 「第一个地址不通、第二个通」时这次会失败。
宁可报「超时」，也不让一次请求拖成 N 倍；下一次重试仍会用到别的地址。

### 前端（被根因放大的四处）

| 处 | 改法 |
| --- | --- |
| `biliHealth.CHECK_TIMEOUT_MS` | 12 s → **25 s**，并写死判据「必须大于后端那 20 s」 |
| `biliHealth.runHealthCheck` | 探测**失败**也退回离线结论，原因放进 `probeError`；只有「连离线都失败」才抛 |
| `BiliLoginSection` | 两种降级各一句准确的话（不再猜「域名解析」）；开始动作时 `onError(null)` 清掉旧红条 |
| `api.request` | 新增可选 `label`，超时消息写成「「扫码登录」请求超时：…（URL）」，URL 仍然保留 |

## 效果（实测）

| | 修复前 | 修复后 |
| --- | --- | --- |
| `status?probe_account=true` | 45 205 ms（未返回） | **574 / 388 ms**，HTTP 200 |
| `POST login/qrcode` | > 45 s | **666 ms**，HTTP 200 |
| 重新体检 | 每次只有离线结论 | 直接拿到账号结论 |

## 风险与回滚

- **只走 IPv4**：若某天 B站 只有 AAAA 记录（目前不存在），请求会失败。回滚只需去掉两个 handler。
- **预算用完不试下一个地址**：见上「取舍」。
- **前端 25 s 比 12 s 长**：点「重新体检」后最长要等 25 秒才会退回离线结论；期间按钮是
  「体检中…」且禁用（已有点击反馈），不会看起来没反应。
- 回滚：`git revert <commit>`，无数据迁移。

## 未覆盖 / 如实说明

- **没有扫完真实二维码**：探针验到「二维码渲染出来、接口 200」就停，没有再拿手机扫一次
  （那需要人）。登录**之后**的链路本轮没碰。
- **「当时那条红条确实来自重试投稿」是推断**：用户没提供操作序列。依据是「错误横幅是页面级的、
  开始新动作时不清」＋「当晚日志里没有 qrcode 请求」（请求 160 秒没回来，访问行根本没写成）。
- **IPv6 黑洞是这台机器的状态**，不是 B站 的属性。代码只做「优先 IPv4」，并没有禁用 IPv6；
  换一台 IPv6 正常的机器同样工作（会退化成只有 IPv4 地址那一批，速度相同）。
- **前端并行跑 vitest 会静默丢文件**：本轮核数用 `--no-file-parallelism`（21 文件 / 291 passed）；
  并行跑同一份代码得到过 20 文件 / 215 passed / 1 failed 的读数，与之不符的读数一律不作数。
- 「点扫码登录时看到的是**重试投稿**的超时消息」这一条，是从「错误横幅是页面级的、上一条不清理」
  与「日志里当晚没有 qrcode 请求」这两条证据推出来的**最合理解释**，没有用户当时的操作序列可核。
