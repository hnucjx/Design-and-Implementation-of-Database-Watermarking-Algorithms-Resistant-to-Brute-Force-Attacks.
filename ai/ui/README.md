# 界面缺陷记录（ui）

本目录记录**每一处界面缺陷与设计瑕疵**：一个问题 = 一个文件 = 一个 commit。

它与 [修复记录（bug-fix）](../bug-fix/README.md) 分工不同：

| | 记什么 | 典型症状 |
|---|---|---|
| `ai/bug-fix/` | **功能坏了** | 报错、任务失败、数据被破坏 |
| `ai/ui/`（本目录） | **界面不对** | 能跑、不报错，但呈现错位、不一致、说不清 |

之所以要单独开一个目录，是因为第二类问题的处境最糟：它**没有堆栈、没有失败用例**，
唯一的证据是「用户看了一眼觉得不对」。这种问题要么被当成主观意见拖下去，
要么被「看着还行」蒙过去。所以本目录的硬要求是：

> **必须把「肉眼看到的差异」变成可测量的数字。**

只有一句「看着不齐」的记录视为未完成。至少要给出：哪个元素、哪个属性、差多少像素、
用什么命令量出来的。

## 记录约定

每个文件按固定小节写，宁可写「未验证」也不要写猜测：

| 小节 | 要求 |
|---|---|
| 问题 | 用户能观察到的现象（截图 + 坐标），不是代码现象 |
| 原因 | 具体到文件/行/属性，附**实测**证据（命令与输出），不写「可能是」 |
| 修复方案 | 改了什么、为什么这么改、**为什么不选另一种改法** |
| 效果 | 修复前后的可对照数字（差几像素、行高多少） |
| 验证 | 自动化断言 + 真实浏览器实测 + 回归结果；新增的断言要**先证明它能抓住这个缺陷** |
| 风险与回滚 | 副作用、回滚方式；影响到别的断点/主题的必须写清 |
| 关联 | 指向相邻缺陷，说明是否同一类失败 |
| 未覆盖 / 如实说明 | **必填的诚实项**：这类缺陷的自动化覆盖边界在哪、本轮没验到的地方 |

记录的插图放 `ai/ui/assets/NNN-*.png`（目前只有 003 用到）：改动是**视觉**的、
而 `docs/assets/screenshots/` 里那四张拍的是默认状态、看不出差别，所以对照图随记录走。
图必须**自解释**（把「哪个是修复前、差多少像素」画在图上），并写清它是怎么生成的 ——
003 的「修复前」那张是用承重注入还原的渲染，不是历史截图，不得当成历史截图引用。

## 一条通用约定：这类缺陷的自动化覆盖边界

本仓库的前端测试跑在 **jsdom** 上，jsdom **不做布局**：`getBoundingClientRect()` 一律返回 0，
`getComputedStyle()` 也算不出真实的盒模型。因此

- **「两个东西是不是对齐」永远无法用单测断言**；
- 能进单测的只有**样式源文层面的不变式**（例如「某个基类不许声明纵向外边距」）；
- 真正的判据是 **CDP 探针 + 真实浏览器实测**：headless Edge + CDP，量 `getBoundingClientRect()`
  与 `getComputedStyle()`，并截图。探针放在被 gitignore 的 `tmp_acceptance/` 下（不进 CI，故非自动化覆盖）。

记录里必须写清哪一部分被自动化覆盖、哪一部分只靠人工/探针，不许含糊成「已修复」。

   （`App.tsx` 的 `applyAnalysisResult()`：`subtitle_languages: settings?.default_subtitle_languages ?? …`，
